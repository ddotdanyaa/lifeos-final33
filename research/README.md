# LifeOS Research Base — инженерный «мозг» разработки (RDD)

Накопительная база знаний для Research-Driven Development. **Правило владельца (2026-07-22):
перед реализацией любой функции — сначала свериться здесь, потом проектировать под LifeOS,
и только потом код.** Никогда не переанализировать заново то, что уже извлечено (Правило №13).

Это не свалка markdown: **компактная навигация**, а детальный каталог функций уже существует —
`docs/DONOR_FUNCTION_CATALOG.md` (160+ функций) и `docs/OSS_DONOR_AUDIT.md` (лицензии/стек). База
`/research` их **не дублирует**, а связывает и достраивает недостающими слоями.

## Как пользоваться (RDD-цикл — Правила №5/№11)

Перед КАЖДОЙ новой функцией:
1. **Найти аналог** — `MASTER_FEATURE_INDEX.md` + `docs/DONOR_FUNCTION_CATALOG.md` (что уже разобрано).
2. **Сравнить реализации** — `MASTER_ARCHITECTURE_INDEX.md` (модели) + `MASTER_ALGORITHM_INDEX.md` (алгоритмы).
3. **Выделить лучшее** — где проще архитектура / сильнее UX / удачнее алгоритм.
4. **Спроектировать под LifeOS** — vanilla JS / IndexedDB / 47 коллекций / proposal→preview→apply→receipt.
5. **Только потом код.** После — отметить статус в `MASTER_FEATURE_INDEX.md`.

## Железные правила (Canon §0 / CLAUDE.md §3.1)

- **Не переносим код и не копируем архитектуру.** Проекты — инженерные ориентиры (идеи/алгоритмы/UX/паттерны).
- **Лицензии:** код можно только MIT/Apache-2.0/BSD и только если стек совместим; AGPL/GPL/MPL/custom — только идеи.
- **Стек-фильтр:** Python/Java/ClojureScript/React-build не встаёт в наш vanilla-браузер → берём концепции.
- **Мутации** — только proposal→preview→apply→receipt (§7). Тяжёлые зависимости — по слову владельца.
