## RR-001 · Семантический разбор захвата (on-device LLM) — 2026-07-22

**Триггер (реальный кейс владельца):** голосовая-поток «выхожу на работу… создай задачу… работаю
с 16:00… подрабатываю в такси до трёх… запишу сколько заработал» → LifeOS вытащил ТОЛЬКО одну
задачу «16:00». Много смыслов в одной записи не разложены; на дневном потоке голосовых инсайтов не будет.

1. **Что за проблема.** `analyzeArtifactInput` (app.js:4613) — разбор по КЛЮЧЕВЫМ СЛОВАМ
   (`isTask`/`isIncome`/`hasAnyText(...)`). Не понимает смысл свободной речи, не декомпозирует
   один захват на несколько типизированных артефактов (смена + доход + задача + проект).
2. **Задачи пользователя.** Накидать сбивчивые русские голосовые → корректно разложить на
   несколько артефактов + связи + инсайты + предложение проекта.
3. **Изученные reference-реализации** (уже исследованы, не переоткрываем — см. MASTER_*):
   Mem0/Cognee/Graphiti/LlamaIndex/Haystack — извлечение сущностей/фактов/триплетов делают
   **LLM-ом**, не правилами. Вывод: семантическая декомпозиция — работа модели, не regex.
4. **On-device ландшафт (веб-ресёрч 2026, grounded):** sweet spot 0.5B–3B Q4. **Qwen2.5-1.5B-Instruct**
   — мультиязычный (вкл. русский), силён в структурном JSON; Llama-3.2-1B тоже годен. **Ниже 1B
   (Qwen2.5-0.5B, gemma-270m) — качество резко падает** на сложном русском. Пути инференса:
   **Ollama** (уже интегрирован) или **Transformers.js/WebGPU** (`@huggingface/transformers` —
   УЖЕ в утверждённом стеке, на нём Whisper), v4 (фев 2026) 71–80% нативной скорости, WASM-фоллбэк.
   Реальность против мифа «27 трлн на iPhone»: это МИЛЛИАРДЫ (0.5–3B, ~400МБ–2ГБ), но да, крутятся
   на телефоне/ноуте и для извлечения достаточно умны.
5. **Внутренние подсистемы LifeOS:** analyzeArtifactInput (анализатор) · proposal-движок
   (drafts→proposal→apply→receipt) · buildOllamaChatPrompt (клиент Ollama) · @huggingface/transformers
   (Whisper) · 47 коллекций/артефактная модель.
6. **Алгоритм (общеинженерный, реализуем сами):** тесный system-prompt + JSON-схема типов артефактов
   → модель отдаёт МАССИВ структурированных намерений → валидация → drafts. При сбое/недоступности —
   фоллбэк на правила.
7. **UX:** тот же ввод; при доступной модели «LifeOS понял» показывает НЕСКОЛЬКО карточек (задача
   16:00 · смена 16:00–19:00 · доход к записи · проект «работа/такси»), каждая — предложение с
   подтверждением. Модель работает в фоне, статус честный (загрузка/не подключено).
8. **Что подходит LifeOS:** локально/приватно (on-device), proposal→receipt, реюз Ollama/Transformers.js,
   без новой категории зависимостей, local-first — преимущество перед серверными донорами.
9. **Что НЕ подходит:** облачные API; большие модели; авто-применение без подтверждения; принудительная
   загрузка модели при первом старте (только opt-in — первый вес 400МБ–2ГБ).
10. **Реализация в LifeOS (направление для Режима DESIGN, НЕ код здесь):**
    - **Этап A (без модели, ценность сразу, offline-always):** усилить правила — ДЕКОМПОЗИЦИЯ
      многосмыслового захвата на несколько drafts (резать по клаузам/намерениям: «работать с 16»,
      «такси», «сколько заработал» → смена + задача + доход-план). Кейс со скриншота должен давать ≥2–3 карточки.
    - **Этап B (семантика, opt-in):** локальный «понять»-проход — реюз Ollama если запущен; иначе
      опциональный Transformers.js **Qwen2.5-1.5B-Instruct** (WebGPU + WASM-фоллбэк), gated + честный
      статус, отдаёт структурированные drafts. Правила остаются фоллбэком (§7).
    - Оба этапа кормят СУЩЕСТВУЮЩИЙ конвейер proposal→apply→receipt (без дублей).
