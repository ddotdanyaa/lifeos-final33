Итоговый аудит

Текущее покрытие: примерно 80–85% того, что нужно для тестируемого MVP.

Что осталось: не новые функции, а правила поведения системы:

	•	как она ошибается;

	•	как объясняет свои решения;

	•	как учится;

	•	как измеряется прогресс;

	•	как проходит реальные пользовательские сценарии.

Именно эти последние 15–20% обычно отличают прототип от продукта, которым действительно начинают пользоваться каждый день. Исследования и практические обзоры AI-продуктов сходятся в том, что доверие создают не столько возможности модели, сколько качественно спроектированные циклы обратной связи, объяснимость и обработка отказов. 



Я, кажется, увидел настоящую проблему.



Ты сейчас пытаешься управлять **через список функций**.



А нужно управлять **через вертикальные пользовательские срезы (vertical slices)**. Именно так обычно и рекомендуют собирать MVP: не по модулям ("чат", "граф", "Whisper"), а по полностью работающим пользовательским сценариям от начала до конца. ([Cursa][1])



Именно поэтому сейчас получается вот так:



> ✅ Whisper есть

> ✅ Graph есть

> ✅ Memory есть

> ✅ Insight есть

> ❌ Пользоваться невозможно.



Потому что сделаны куски системы, а не законченные сценарии.

# И теперь самое главное



Вот это, как мне кажется, вообще должно стать **новым правилом для Cloud Code**:



> **Запрещено начинать новую функцию, пока предыдущий пользовательский сценарий не закрыт полностью. Сценарий считается закрытым только тогда, когда обычный человек может пройти его от начала до конца без объяснений, без технических терминов и без ощущения, что перед ним "демо". Если сценарий требует инструкции — он не завершён.**



Это радикально меняет способ разработки. Вместо "готово 73% модулей" появляется простой критерий: **сколько жизненных сценариев человек реально может использовать ежедневно**. Именно это и позволяет получить настоящий MVP, а не набор полуготовых возможностей. ([risetech.ai][2])

Короткий промпт для Claude Code



Your goal is NOT to build features. Your goal is to maximize the learning ability of LifeOS.



Before implementing anything:



1. Search the entire repository.

2. Use every available Claude Code Skill that is relevant.

3. Reuse existing implementations before creating new ones.

4. Prefer extending architecture instead of adding parallel systems.

5. Think like a principal engineer and product researcher simultaneously.



Every feature must increase one or more of these capabilities:



- continuous learning

- memory quality

- entity resolution

- graph connections

- knowledge extraction

- insight generation

- context understanding

- personalization

- long-term adaptation

- explainability



Always ask:

"Does this make the system smarter after processing one more user input?"



If the answer is no, redesign it.



Never implement isolated CRUD pages.

Never store raw data without extracting knowledge.

Every new artifact must enrich the knowledge graph.



Think in terms of:

Raw Input → Understanding → Entities → Relationships → Knowledge → Insights → Decisions → Learning → Better Future Predictions.

## **ПРИОРИТЕТ ПЕРЕВЕДЁН**



**До 1 августа:**

Не система для Володи. **Система для владельца**, который сам тестирует и закидывает мысли.



**Минимум (блокирующий для старта 1 августа):**



1. **Self-Learning Loop**

   - Владелец закидывает идею: "месячный прогноз финансов"

   - Система: видит похожие старые идеи → группирует → помечает как дубль или как уточнение

   - Результат: владелец видит "найдено 3 похожих идеи от 15.07, 22.07, 27.07"



2. **Insights → Визуал**
