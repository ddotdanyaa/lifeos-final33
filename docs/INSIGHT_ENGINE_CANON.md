Лицензий нет как проблемы, потому что мы **не переносим код и не копируем архитектуру** — берём
только принципы и функциональные возможности и реализуем их в собственной артефактной
архитектуре LifeOS. Собери канон из лучших продуктов/репозиториев по инсайтам, knowledge
graph, памяти, RAG, визуальному мышлению — и по нему веди работу, как по джентльсету».

Этот файл — НЕ обзор приложений. Это рабочая инструкция: карта доноров-ориентиров + процесс
их разбора + связка с очередью внедрения `docs/INSIGHT_IMPLEMENTATION_QUEUE.md`.

## 0. Железные правила (обязательны для каждого пункта ниже)

- **Не переносим код. Не копируем архитектуру.** Реализуем только *принципы* и *функции* в
  vanilla-JS / IndexedDB / локально-первой артефактной модели LifeOS (47 коллекций, schema v3,
  proposal+receipt+capability контракты). Это снимает лицензионный вопрос по сути: чужой код
  не оказывается в нашем репозитории.
- **Стек-фильтр жёсткий.** Почти все доноры ниже — Python/сервер/облако/React. Из них берём
  **алгоритм/идею/UX-паттерн**, а не рантайм. Никаких новых тяжёлых рантайм-зависимостей без
  явного слова владельца (правило CLAUDE.md §2). Локальный AI у нас уже есть: `@huggingface/
  transformers` (эмбеддинги/Whisper), `minisearch` (лексический поиск), Ollama (LLM) — новые
  фичи строим поверх них.
- **Контракты безопасности LifeOS выше любой донор-фичи (§7).** «Knowledge builds itself» —
  да, но через **proposal → preview → apply → receipt**, никогда не скрытой мутацией графа/
  памяти. Это, кстати, ровно паттерн Tana «proposals before write», так что доноры и наши
  правила здесь совпадают.
- **Терминология:** «что рекомендуется адаптировать / реализовать / внедрить / изучить», не
  «украсть».

## 2. Доноры по модулям (предварительный разбор; глубокий — по процессу §4)

### Knowledge Graph & Relations

# 🥇 Logseq (MIT, open source)
## Почему выбран
Полностью открытый движок графовой базы на блоках с двунаправленными связями и запросами —
эталон «граф из блоков», ближайший по духу к артефактному графу LifeOS.
## Что рекомендуется изучить
Block model · page/block references · linked & unlinked references · block queries ·
property/page-properties · граф-индекс · «journals» как daily-поток.
## Какие пользовательские проблемы это решает
| Функция | Проблема пользователя |
| --- | --- |
| Linked references | связи видны в обе стороны без ручной работы |
| Unlinked references | система сама предлагает, где ещё упомянуто |
| Block queries | срез знаний без экспорта/таблиц |
| Page properties | типизация без отдельной схемы |
## Почему потенциально полезно для LifeOS
Усиливает наш граф «unlinked references» (кандидаты связей) и запросами-как-представлениями;
daily-журнал ложится на наш поток capture.

# 🥇 Graphiti (идея-донор, Python/сервер — только алгоритмы)
## Почему выбран
Одна из сильнейших открытых реализаций AI Knowledge Graph с временным измерением.
## Что рекомендуется изучить
Entity Extraction · Relationship Extraction · Temporal Graph · Incremental Updates ·
Community Detection · Graph Traversal · Edge Ranking.
## Какие пользовательские проблемы это решает
| Функция | Проблема пользователя |
| --- | --- |
| Entity Extraction | не хочет вручную создавать сущности |
| Relationship Extraction | связи появляются автоматически |
| Temporal Graph | сохраняется история знаний (что когда узнал) |
| Community Detection | находятся скрытые группы информации |
| Incremental Updates | не нужно перестраивать весь граф |
## Почему потенциально полезно для LifeOS
Прямо усиливает артефактный граф и качество инсайтов; уменьшает ручной труд. Реализуем как
*детектор кандидатов* (edge ranking по overlap), выводимый в инсайты/предложения — не скрытую
мутацию.

# 🥈 Neo4j / Cypher (идея-донор, эталон графовых БД)
## Что рекомендуется изучить
модель property-graph, паттерны обхода, ранжирование путей, degree/centrality.
## Проблемы/польза
Центральность узла = «важные хабы твоих знаний»; паттерны обхода = «локальный граф N хопов»
(у нас уже есть G2.6). Берём *концепции ранжирования*, не движок.

# Juggl / Breadcrumbs / Excalibrain (Obsidian-плагины, идея-донор)
## Что рекомендуется изучить
Juggl — интерактивный граф с типами рёбер; Breadcrumbs — иерархии (up/down/same) поверх
связей; Excalibrain — авто-раскладка «родитель/ребёнок/друг» вокруг фокуса.
## Проблемы/польза
Типы рёбер (входящее/исходящее у нас уже есть — G2.7), иерархическая навигация (родитель→
ребёнок), «мозг вокруг узла». Внедрять как слои поверх нашего canvas.

# Capacities / Tana (продукты, идея-донор объектной модели)
## Что рекомендуется изучить
типизированные объекты (Person/Book/Project/Meeting/Company/Idea), у каждого своя schema;
Tana — supertags, typed nodes, relations, «proposals before write», AI extraction.
## Проблемы/польза
У нас это уже фундамент (47 типизированных коллекций + proposal-engine). Из Tana берём
**авто-извлечение сущностей → предложение типизированного узла перед записью**.

### Semantic Search & RAG

# 🥇 Smart Connections (Obsidian, MIT-подобный, идея-донор)
## Почему выбран
Каноничная фича «связано по смыслу»: локальные эмбеддинги → ближайшие заметки к текущей.
## Что рекомендуется изучить
локальный embedding-индекс, cosine-similarity ранжирование, «connections pane», инкрементное
переиндексирование при правке.
## Проблемы/польза
| Функция | Проблема |
| --- | --- |
| Semantic neighbours | находит неожиданные связи, которых нет по ключевым словам |
| Local embeddings | приватно, офлайн |
Реализуем поверх нашего `@huggingface/transformers` + semanticIndex (если модель эмбеддингов
недоступна — честный лексический фоллбэк, никакой имитации).

# 🥇 NotebookLM (Google, продукт, идея-донор grounded-AI)
## Что рекомендуется изучить
Source Grounding → Citation Engine → Semantic Chunking → Reasoning. Модель почти не
фантазирует, всё привязано к источникам.
## Проблемы/польза
У нас уже есть цитаты в чате (C1.4). Углубляем: chunk-level цитаты, «ответ только из твоих
источников», отказ вместо выдумки — ложится на наш AI-memory-gate (§P5.3).

# Omnisearch / LlamaIndex (идея-донор поиска/RAG)
## Что рекомендуется изучить
Omnisearch — fuzzy+ранжирование по всей базе; LlamaIndex — chunking, node-postprocessing,
hybrid retrieval (лексика+вектор), reranking.
## Проблемы/польза
Гибридный поиск (minisearch + эмбеддинги) и reranking для «Памяти»/чата. Только алгоритмы.

### Memory Systems

# 🥇 Mem0 (идея-донор долговременной памяти AI)
## Что рекомендуется изучить
embedding-память · memory scoring (importance) · forgetting/decay · semantic recall ·
дедупликация фактов.
## Проблемы/польза
| Функция | Проблема |
| --- | --- |
| Importance scoring | наверх всплывает главное, не шум |
| Forgetting/decay | старое тихо гаснет, не мешает |
| Semantic recall | «вспомни про X» находит по смыслу |
Реализуем как скоринг артефактов (свежесть+частота+связность) и «пора вспомнить» resurfacing —
поверх наших коллекций, честной арифметикой.

# Zep (идея-донор персональной памяти агентов)
## Что рекомендуется изучить
message/session memory, summary-over-time, извлечение фактов из диалога, релевантность по
времени.
## Проблемы/польза
Сводка-по-времени для чата и «фактов из разговоров» → предложения в память (через proposal).

### Agents & Orchestration

# LangGraph (идея-донор оркестрации агентов)
## Что рекомендуется изучить
граф состояний агента, узлы-инструменты, ветвление/циклы, human-in-the-loop, checkpoints.
## Проблемы/польза
Наш Builder/Agents уже preview→approve→apply. Берём модель «граф состояний + human-in-the-
loop checkpoint» для сценариев (это и есть тот «сценарий», который владелец хочет запускать).

### Local-first Knowledge Base

# OpenKnowledge (СВЕЖИЙ — требует перепроверки перед разбором)
## Статус
Заявлен как локальная Git-совместимая база знаний для людей и AI-агентов с MCP/Markdown.
Перед адаптацией Claude Code обязан подтвердить репозиторий, лицензию и реальный набор фич
(не полагаться на память — прямой аудит LICENSE и README).
## Потенциальная польза
Git-совместимость и MCP-мост человек↔агент — созвучно локально-первому LifeOS.

### Visual Thinking & UI

# Heptabase / Obsidian Canvas (идея-донор пространственного мышления)
## Что рекомендуется изучить
Whiteboard, card system, spatial memory, visual clustering, bidirectional graph на доске.
## Проблемы/польза
Ложится на будущий W1 Whiteboard (Excalidraw-ядро) и W3 Doc↔Canvas — пространственная
кластеризация как визуальный слой инсайтов.

### Query & Views

# Dataview (Obsidian, идея-донор запросов-как-представлений)
## Что рекомендуется изучить
DQL/inline-запросы, представление артефактов таблицей/списком/календарём по свойствам.
## Проблемы/польза
«Данные ≠ представление» (наш принцип §6): один артефакт → таблица/лента/таймлайн по запросу.

## 4. Что должен сделать Claude Code для КАЖДОГО донора (процесс)

1. Изучить репозиторий (там, где доступен) — структуру, ядро, README.
2. Изучить документацию.
3. Изучить Wiki (если есть).
4. Изучить блог разработчиков / инженерные заметки.
5. Изучить RFC / ADR / дизайн-доки (если есть).
6. Выделить ВСЕ функции.
7. Для каждой функции определить: какую проблему пользователя решает; как реализована; какие
   алгоритмы; насколько применима к артефактной архитектуре LifeOS.
8. **Не переносить код.**
9. **Не копировать архитектуру.**
10. Реализовать только принципы и функции в рамках артефактной архитектуры LifeOS — через
    proposal→preview→apply→receipt, поверх vanilla-JS/IndexedDB/уже одобренных движков.

Результат каждого разбора → строка(и) в `docs/INSIGHT_IMPLEMENTATION_QUEUE.md` с донор-
источником и конкретной реализуемой фичей. Оттуда идёт обычный конвейер (пакет → гейты →
commit+push → отметка `[x]`), тот же, что закрыл весь предыдущий донорский план.

> Важно: блоки выше — предварительный анализ. Полный каталог функций Claude Code получает сам
> при глубоком разборе каждого репозитория/документации, дополняя очередь.
