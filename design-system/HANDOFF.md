# LifeOS — передача дизайна в код (Claude Code)

Дизайн уже готов и лежит рядом. Это **не концепт и не картинки** — это работающий интерфейс на HTML, который можно открыть в браузере и потыкать. Твоя задача — не придумывать UX заново, а подключить к нему настоящие данные.

## Что открывать

8 файлов, каждый открывается напрямую в браузере:

| Файл | Экран | Роль |
|---|---|---|
| `Home.dc.html` | Дом | универсальный ввод, одно лучшее действие, чат-ответы, решения, инсайты |
| `Universal Capture.dc.html` | Поток | входящее из всех источников, разбор дня, прогноз, «нужно уточнить», применение |
| `Artifact Inspector.dc.html` | Объект | вердикт, источники, связи, хронология, противоречия |
| `Today.dc.html` | Сегодня | блоки дня, конфликты календаря, задачи с эффектом на цель |
| `Graph.dc.html` | Граф | карта связей (force layout) + вопросы о жизни |
| `Agents.dc.html` | Агенты | план → подтверждение → исполнение → отчёт → квитанция |
| `Builder.dc.html` | Builder | рабочие пространства, свои сущности, представления, правила |
| `Control.dc.html` | Контроль | что внутри, маршруты наружу, журнал чеков, откат |

Плюс `support.js` (рантайм, не трогать) и `assets/lifeos-icon.svg`.

## Как запустить локально

Файлы ссылаются друг на друга относительными путями, поэтому нужен любой статический сервер (по `file://` навигация между экранами будет ломаться):

```bash
cd <папка проекта>
python3 -m http.server 8080
# открыть http://localhost:8080/Home.dc.html
```

Или `npx serve .` — без разницы. Никакой сборки, npm-зависимостей и бэкенда для просмотра не нужно.

## Как это устроено внутри

Каждый `.dc.html` — самодостаточный файл из двух частей:

1. **Разметка** внутри `<x-dc>…</x-dc>` — вся вёрстка инлайновыми стилями, никаких CSS-классов.
2. **Логика** в `<script type="text/x-dc" data-dc-script>` — `class Component extends DCLogic` с `state`, обработчиками и методом `renderVals()`, который возвращает всё, что подставляется в разметку через `{{ }}`.

Демо-данные лежат константами в начале скрипта каждого файла (`ITEMS`, `RESULT`, `N`, `E`, `AGENTS`, `SEARCH`, `LENS` и т.п.). **Это точки подключения бэкенда** — заменяются на реальные данные, разметка не меняется.

Как переносить в свой стек — на твой выбор (React/Vue/Svelte/что угодно). Разметка читается напрямую как JSX: инлайновые стили, никакой магии. Важно сохранить не пиксели, а поведение из списка ниже.

## Что нельзя потерять при переносе

Это законы продукта, они зашиты в интерфейс намеренно:

1. **Одна модель — артефакты.** Дом/Работа/Финансы/Здоровье — это срезы одной модели, а не разделы. Переключение меняет ранжирование, не данные.
2. **Пользователь никогда не выбирает тип, папку и тег.** Ввод один, классификацию делает система.
3. **Ничего не пишется молча.** Разбор даёт *предложения*; применение создаёт чек с номером и возможностью откатить.
4. **Дубликаты не создаются.** Повторное упоминание усиливает существующий объект («уже есть такая задача — не создаю вторую»).
5. **У каждого утверждения есть источник и уверенность.** «Из голосового 21 июл 21:20», «уверенность 84%».
6. **Гейт по уверенности.** Высокая → одно лучшее действие. Низкая → вопрос в «Нужно уточнить», а не предложение.
7. **Вопрос остаётся вопросом.** Если пользователь спрашивает — система отвечает текстом с цитатами и явно пишет, что ничего не создала.
8. **Граф отвечает «почему», а не «что связано».** У каждой связи: тип (блокирует / противоречит / следствие / влияет / питает), сила, объяснение, время появления.
9. **Агент не делает необратимое без подтверждения.** Виден план, шаги, права, журнал, откат.
10. **Всё локально.** Маршрут наружу включается вручную, и рядом написано, что именно уйдёт.

## Что должен отдавать бэкенд (по экранам)

Ниже — минимальный контракт. Названия полей свои, важен состав.

**Поток / вход**
- `POST /capture` — текст, аудио, файл, ссылка. Возвращает артефакт со `source` (telegram / recorder / laptop / file) и временем. Тип не определяется на этом шаге.
- `GET /stream?date=` — сырые объекты дня, сгруппированные по времени суток, у каждого: вид, длительность/размер, превью.
- Распознавание вопроса: `POST /ask` — ответ + список цитат (id артефактов). Ничего не создаёт.

**Разбор дня**
- `POST /digest/run` — стадии с прогрессом: расшифровка → чтение файлов → извлечение сущностей → сверка с графом → связи → паттерны. Счётчики: голосовых, сущностей, совпадений (не дублей), новых связей.
- Ответ: `proposals[]` — `{kind, title, summary, why, confidence, sources[], target_id?}`, где `target_id` есть, если это обновление существующего объекта, а не новый.
- `low_confidence[]` — то же, но как вопросы с вариантами ответа.
- `forecast[]` — `{goal_id, probability, previous, explanation}` и `underestimated[]` — `{kind: деньги|время|нагрузка, text}`.
- `POST /digest/apply` — принимает выбранные id, возвращает `receipt_id` и diff графа. `POST /digest/undo` — откат по receipt_id.

**Объект**
- `GET /artifact/:id` — вердикт (одно предложение о состоянии), факты с провенансом, `sources[]` (что именно дал каждый источник), `relations[]` (тип, сила, объяснение, confidence), таймлайн по месяцам (разговоры против действий), `conflicts[]` с вариантами решения и ценой каждого.
- `POST /artifact/:id/resolve` — выбранный вариант; пересчитывает вердикт, срок, следующий шаг, пишет чек.

**Граф**
- `GET /graph` — `nodes[]` (id, label, cluster, weight, kind, mentions, summary) и `edges[]` (from, to, type, strength, why, created_at).
- `GET /graph/node/:id` — соседи с объяснениями, цепочка влияния до цели, «что рассыплется без этого узла», изменения за 7 дней.
- `GET /graph/answer/:question` — готовые ответы на: кто влияет на продуктивность, что тормозит цель, какие цели противоречат, почему выросли расходы, где теряется энергия, что изменилось за неделю, какие мысли повторяются. У каждого: вывод, объяснение, данные для визуализации, `evidence[]`.

**Дом / Сегодня**
- `GET /home?space=` — `best_action` с `confidence` и «почему это, а не другое», `others[]`, `decisions[]` (что ждёт решения с вариантами), `insights[]`.
- `POST /home/recalc`, `POST /home/defer` — пересчёт и «не сейчас».
- `GET /today` — блоки дня с источником блока, конфликты календаря с вариантами переноса, задачи с полем «эффект на цель», `deferred[]` с причиной, почему система убрала.

**Агенты**
- `GET /agents` — у каждого: триггер, шаги, права (что может и чего не может), журнал чеков.
- `POST /agents/:id/plan` → `POST /agents/:id/confirm` → поток исполнения по шагам → `report` + `receipt`. Необратимые шаги помечены и требуют подтверждения.

**Builder**
- `GET /workspaces`, `POST /workspaces/:id` — состав закреплённых линз, порядок, ширина.
- `POST /entities` — своя сущность: имя, поля, представление (список/доска/календарь/граф), правило. Сущность автоматически получает контракт объекта: id, источник, связи, история, уверенность, права, чеки, экспорт.

**Контроль**
- `GET /control` — состав хранилища, маршруты наружу с точным описанием, что уйдёт, журнал чеков.
- `POST /control/route/:id`, `POST /control/receipt/:id/undo`, `POST /control/export`, `POST /control/stop`.

## Порядок работ, который я бы предложил

1. Поднять статикой, пройти сквозной маршрут: Дом → Поток → Разобрать → Применить → Объект → Граф → Агенты → Контроль. Убедиться, что поведение понятно.
2. Заменить константы демо-данных на реальные вызовы — по одному экрану, начиная с Потока (вход + разбор). Разметку не трогать.
3. Подключить Hermes/Telegram как источник в `POST /capture` со `source: telegram`.
4. Реализовать сверку с графом до создания объектов (пункт 4 законов) — это главное, что отличает продукт от заметочника.
5. Только после этого — прогноз, паттерны и агенты.
